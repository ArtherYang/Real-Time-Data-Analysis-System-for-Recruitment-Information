## ADR-001：后端 Web 框架

### 背景
需要选择一个 Python Web 框架来构建 RESTful API 服务，支撑岗位查询、分析计算、用户管理等功能。

### 候选方案

| 维度 | Flask | FastAPI | Django |
|------|-------|---------|--------|
| 学习曲线 | ★★☆ 低 | ★★☆ 低 | ★★★ 高 |
| 异步支持 | 需扩展 (Quart) | 原生 async/await | 需扩展 (Django 4.1+) |
| ORM 集成 | 可选 SQLAlchemy | 可选 SQLAlchemy | 内置 Django ORM |
| API 文档 | 需扩展 (Flask-RESTX) | 内置 Swagger/OpenAPI | 需扩展 (DRF) |
| 生态丰富度 | ★★★ 高 | ★★★ 高 | ★★★ 最高 |
| 课程适配 | 符合教学要求 | 较新技术 | 重量级，不利于敏捷迭代 |
| 社区活跃度 | 持续活跃 | 快速增长 | 长期活跃 |

### 决策
**选择 Flask**（v3.x）

### 理由
1. **学习成本可控**：Flask 是 Python Web 入门首选，轻量级设计适合课程项目的敏捷迭代节奏
2. **灵活性强**：不做技术锁定，可自由搭配 SQLAlchemy、Celery 等组件
3. **生态成熟**：Flask-CORS、Flask-JWT 等扩展丰富，踩坑成本低
4. **课程评审友好**：相比 FastAPI 的新特性，Flask 的代码结构更易被评审老师理解
5. **足够支撑当前需求**：项目并发量不高（<500 QPS），Flask 同步模式完全够用

### 后果
- API 文档需额外集成 Flask-RESTX 或手动编写 Swagger
- 后续如需 WebSocket 实时推送需引入 Flask-SocketIO

## ADR-002：数据库（业务数据）

### 背景
存储岗位信息、用户数据、分析缓存等结构化数据，要求支持复杂查询和事务。

### 候选方案

| 维度 | MySQL 8.0 | PostgreSQL | MongoDB |
|------|-----------|------------|---------|
| 数据类型 | 关系型 | 关系型 + JSON/数组 | 文档型 |
| 复杂查询 | ★★★ JOIN 优秀 | ★★★ 窗口函数强 | ★☆☆ 聚合管道 |
| 事务支持 | ★★★ ACID | ★★★ ACID | ★★☆ 有限 ACID |
| 全文搜索 | ★★☆（可配合 ES） | ★★★ 内置成熟 | ★★★ 内置 |
| 运维复杂度 | ★☆☆ 低 | ★★☆ 中 | ★★☆ 中 |
| 课程评审 | 首选，行业主流 | 需解释选型理由 | 需说明非关系型的必要性 |
| 生态工具 | Navicat/Workbench 丰富 | pgAdmin 成熟 | Compass 够用 |

### 决策
**选择 MySQL 8.0**

### 理由
1. **行业标准**：招聘数据天然是结构化的（岗位名、公司、薪资范围、城市），关系型数据库最合适
2. **课程覆盖**：MySQL 是数据库课程教学标准，评审老师认可度高
3. **生态成熟**：PyMySQL + SQLAlchemy ORM 组合稳定可靠
4. **性能足够**：预计日增量 1-5 万条，年度总量 500 万-2000 万条，MySQL 单表千万级轻松应对
5. **内置功能**：8.0 的窗口函数、JSON 列、CTE 等满足所有分析查询需求

### 后果
- 如后续需要地理空间查询（GIS），需评估是否引入 PostGIS 或应用层计算
- 全文搜索能力一般，复杂搜索场景配合 Elasticsearch

## ADR-003：爬虫框架

### 背景
需要从多个招聘平台（BOSS直聘、智联、前程无忧等）采集招聘数据。

### 候选方案

| 维度 | Scrapy | 自研 (Requests + BS4) | Selenium / Playwright |
|------|--------|----------------------|-----------------------|
| 学习曲线 | ★★★ 中等 | ★★☆ 低 | ★★★ 高 |
| 异步并发 | 内置 Twisted 引擎 | 需手动实现 | ❌ 单浏览器实例 |
| 中间件 | Pipeline/Downloader 丰富 | 需手动实现 | ❌ |
| 反爬对抗 | IP 代理中间件成熟 | 灵活可控 | 指纹识别风险高 |
| 调试难度 | ★★☆ 有日志系统 | ★☆☆ 直接 print | ★★★ headless 难调试 |
| 适用场景 | 大规模通用爬取 | 小程序/定制化 | 强 JS 渲染页面 |

### 决策
**选择自研方案（Requests + BeautifulSoup4 + 可选 Selenium）**

### 理由
1. **平台特性差异大**：三大招聘平台页面结构、反爬策略、数据格式完全不同，Scrapy 的"统一 Pipeline"反而不灵活
2. **采集规模有限**：课程项目仅需稳定采集 3-5 个渠道，不是万站级爬取，Scrapy 的中间件体系用不上
3. **反爬对抗优先**：BOSS直聘等平台反爬强度高，需要精细控制请求间隔、UA 轮换、Cookie 管理——自研代码更可控
4. **接口优先**：部分平台有未公开 API，用 requests 直接发请求比 Scrapy 的 Spider 更直接
5. **学习价值**：从零实现爬虫架构比配置 Scrapy 更能体现工程能力

### 后果
- 需要自行实现重试、限速、去重等基础设施（已在 `base.py` / `anti_crawl.py` 中完成）
- 如需扩展到 10+ 渠道，可能需要重新评估 Scrapy

## ADR-004：缓存

### 背景
分析计算（薪资统计、岗位排名、技能词云等）需要遍历大量数据，每次请求都实时计算会导致接口响应慢。

### 候选方案

| 维度 | Redis | Memcached | 内存字典 |
|------|-------|-----------|---------|
| 数据结构 | String/Hash/Set/ZSet 丰富 | 仅 String | Python dict |
| 持久化 | RDB + AOF | ❌ 纯内存 | ❌ |
| 过期策略 | TTL 自动过期 | 支持 TTL | 需手动实现 |
| 分布式 | ★★★ 天然支持 | ★★★ 支持 | ❌ 单进程 |
| 运维复杂度 | ★★☆ 中（需安装服务） | ★☆☆ 低 | ★☆☆ 零成本 |
| 生态 | Python redis-py 成熟 | 成熟 | 内置 |

### 决策
**选择 Redis**

### 理由
1. **数据结构匹配需求**：Sorted Set 天然适合岗位热度排名，Hash 适合缓存每类分析结果
2. **TTL 自动过期**：分析缓存 1 小时自动失效，无需手写过期逻辑
3. **复用性强**：Redis 同时作为 Celery 消息代理和结果后端，一个组件解决两个需求
4. **生态标准**：Redis 是业界缓存首选，课程评审无争议
5. **未来扩展**：如需实现实时更新推送，Redis Pub/Sub 可直接使用

### 后果
- 增加了运维依赖（Docker Compose 中已配置）
- 缓存失效策略需持续调优

## ADR-005：前端框架

### 背景
需要搭建数据可视化展示平台，包含看板大屏、岗位检索、图表交互等功能。

### 候选方案

| 维度 | Vue 3 | React 18 | 纯 HTML+ECharts |
|------|-------|----------|-----------------|
| 学习曲线 | ★★☆ 低（中文文档好） | ★★★ 高（JSX/Hooks 概念多） | ★☆☆ 最低 |
| 组件生态 | Element Plus / Vant | Ant Design / MUI | ❌ 需自建 |
| 状态管理 | Pinia（官方推荐） | Redux / Zustand | ❌ |
| ECharts 集成 | vue-echarts 成熟 | echarts-for-react | 原生 JS |
| 构建工具 | Vite（快） | Vite（快） | ❌ |
| SEO | SSR 较复杂 | Next.js 成熟 | ❌ 不适用（后台系统） |

### 决策
**选择 Vue 3 + Vite + Element Plus**

### 理由
1. **学习成本最低**：中文文档质量高，模板语法直觉，适合快速开发
2. **组件丰富**：Element Plus 提供 Table、Form、Dialog 等大量中后台组件
3. **ECharts 集成流畅**：vue-echarts 封装完善，响应式更新方便
4. **Vite 构建极快**：HMR 热更新秒级，开发体验好
5. **课程评审友好**：Vue 是国内高校前端教学主流

### 后果
- 后台管理系统不需 SSR，Vue 的 SPA 模式完全满足
- 如需移动端适配，Element Plus 响应式能力有限

| 中文文档 | ★★★ 完善 | ★★★ 完善 | ★☆☆ 英文为主 |

| 地图组件 | ★★★ 内置中国地图 | ★★☆ 需额外配置 | ★☆☆ 需手写 |
| 词云 | ★★★ wordCloud 扩展 | ★★☆ | ★★☆ |
| 大屏适配 | ★★★ resize 自动 | ★★☆ | ★☆☆ |
| 移动端 | ★★☆ | ★★★ 更好 | ★★☆ |

### 决策
**选择 ECharts**

### 理由
1. **图表最全**：折线图、柱状图、饼图、热力图、地图、词云等需求全部内置覆盖

- 极端大数据量（10万+ 数据点）时需配合降采样
- 定制化程度不如 D3.js，但对本项目的图表需求已足够

## ADR-007：容器化方案

### 背景
需要在本地开发环境和课程演示环境之间保证一致性。

### 候选方案

| 维度 | Docker + Docker Compose | Kubernetes (K8s) | 直接安装 |
|------|------------------------|-------------------|---------|
| 学习成本 | ★★☆ 中 | ★★★ 最高 | ★☆☆ 低 |
| 环境一致性 | ★★★ 镜像保证 | ★★★ 镜像保证 | ★☆☆ 各自配置 |
| 服务编排 | Compose 文件 200 行 | Helm Chart 复杂 | ❌ |
| 资源占用 | 低（少量容器） | 高（至少 4GB 内存） | 最低 |
| 适用场景 | 开发 + 单机部署 | 生产集群 | 个人开发 |
| 课程评审 | 符合现代 DevOps 要求 | 过重，不适用 | 缺少工程实践 |

### 决策
**选择 Docker + Docker Compose**

### 理由
1. **规模匹配**：项目是 5-8 个服务的单体应用，Compose 是最合适的编排工具
2. **一键启动**：`docker compose up -d` 即可启动全部服务，方便评审演示
3. **环境一致**：Python 版本、MySQL 版本、Redis 版本在镜像中锁定
4. **K8s 过重**：课程项目不需要集群调度、自动伸缩、服务网格等 K8s 特性
5. **学习价值**：Docker 是业界标配，Compose 是理解容器编排的入门

### 后果
- 如后续需要多机部署，需迁移到 K8s（但课程项目无此需求）

## ADR-008：消息队列/任务调度

### 背景
采集任务（爬虫运行可能持续数分钟）和离线分析任务（批量计算）不应阻塞 API 请求。

### 候选方案

| 维度 | Celery + Redis | 自研线程池 | APScheduler |
|------|---------------|-----------|-------------|
| 异步任务 | ★★★ 成熟 | ★☆☆ 需手写 | ★☆☆ 不支持 |
| 定时调度 | Celery Beat | 需手写 | ★★★ 成熟 |
| 重试机制 | 内置指数退避 | 需手写 | ❌ |
| 任务监控 | Flower 面板 | ❌ | ❌ |
| 运维复杂度 | ★★☆ 需额外 Worker | ★☆☆ 进程内 | ★☆☆ 进程内 |

### 决策
**选择 Celery + Redis（暂缓实施）**

### 理由
1. **当前阶段**：爬虫数据量不大（单次采集 <1000 条），同步执行可接受
2. **架构预留**：代码已按 Celery 任务模式组织（`tasks/crawl_tasks.py`），配置到位
3. **后续按需启用**：当采集任务耗时超过 30 秒或需要定时调度时，启动 Celery Worker 即可
4. **复用 Redis**：消息代理和结果后端都用 Redis，不引入新依赖

### 后果
- 当前 `tasks/crawl_tasks.py` 中的 Celery 装饰器代码暂不运行
- 启用的时间点：M1 阶段后期，采集任务需要定时调度时
