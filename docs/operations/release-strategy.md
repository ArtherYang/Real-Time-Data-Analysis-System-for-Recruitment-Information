## 一、灰度发布策略

### 概述
采用**3 阶段渐进式发布**，逐步扩大流量比例，每个阶段观察稳定性后再进入下一阶段。

### 发布流程

```
Stage 1 (10%)          Stage 2 (50%)         Stage 3 (100%)
    │                      │                      │
    ├── 观察 30min ────────├── 观察 1h ───────────├── 全量完成
    │                      │                      │
    └── 异常则回滚         └── 异常则回滚         └── 监控持续运行
```

### Nginx 灰度配置示例

```nginx
# 灰度发布：按权重分流
upstream backend_gray {
    server backend-stable:5000 weight=90;   # 稳定版本
    server backend-canary:5000 weight=10;   # 灰度版本
}

upstream frontend_gray {
    server frontend-stable:80 weight=90;
    server frontend-canary:80 weight=10;
}
```

### Docker Compose 灰度部署

```bash
# 1. 启动灰度实例（使用新版本镜像）
docker-compose -f docker-compose.yml -f docker-compose.canary.yml up -d

# 2. 逐步调整权重
# 10% → 等待监控 30 分钟
# 50% → 等待监控 1 小时
# 100% → 关闭旧版本

# 3. 全量切换
docker-compose up -d backend frontend  # 滚动更新
docker-compose stop backend-stable frontend-stable  # 停旧版本
```

### 灰度阶段观察项

| 阶段 | 时长 | 观察指标 | 回滚条件 |
|------|------|---------|---------|
| 10% | 30 min | 错误率、P99 延迟 | 错误率 > 1% 或 P99 翻倍 |
| 50% | 1 hour | 错误率、延迟、资源使用 | 错误率 > 旧版本 2x |
| 100% | 持续 | 全部监控指标 | - |

## 二、回滚机制

### 回滚触发条件
- 接口错误率 > 5%（持续 5 分钟）
- P99 延迟 > 2x 基线
- 数据采集完全中断
- 安全漏洞被发现
- 用户反馈重大 Bug

### 回滚步骤

#### 镜像回滚
```bash
# 方案 A：标签回滚
docker tag ghcr.io/rdas-backend:stable ghcr.io/rdas-backend:rollback
docker-compose pull backend frontend
docker-compose up -d backend frontend

# 方案 B：指定具体版本
export IMAGE_TAG=v1.2.0
docker-compose -f docker-compose.yml \
  -f docker-compose.override.yml up -d
```

#### 数据库回滚
```sql
-- 仅在有 schema 变更时需要
-- 回滚脚本应与升级脚本配套存放
-- 路径: db/migrations/rollback/<version>.sql

-- 示例：删除新增的列
ALTER TABLE jobs DROP COLUMN IF EXISTS new_field;
```

#### 配置回滚
```bash
# 从 Git 恢复上一版本的配置
git checkout v1.2.0 -- docker-compose.yml nginx.conf .env.example
docker-compose up -d
```
